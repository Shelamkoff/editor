# План стабилизации и рефакторинга Rector перед публикацией

## 1. Назначение документа

Этот план объединяет подтверждённые результаты архитектурного, функционального, производительного, безопасностного и документационного аудита редактора Rector и его расширений.

План относится только к редактору, его блочным плагинам, внутристрочным инструментам, внутристрочным плагинам и рендерерам. Vue-приложение, backend и самостоятельные библиотеки `@shelamkoff/event-bus`, `@shelamkoff/color-picker`, `@shelamkoff/cropper`, `@shelamkoff/carousel` и `@shelamkoff/expose` в этот цикл не входят.

Основные ограничения:

- существующая функциональность не урезается;
- обратную совместимость сохранять не требуется;
- серверная интеграция Poll реализуется через абстрактный адаптер, без зависимости от конкретного backend;
- VitePress остаётся источником полной документации и не входит в npm-пакет;
- термины «Зум» и «Персона» являются утверждёнными и не заменяются;
- изменения стиля кода без измеримого архитектурного или функционального эффекта не выполняются.

## 4. Этап 1. Зафиксировать публичный контракт сохранения

### Исходная проблема — устранена

Публичный `save()` был объявлен асинхронным, но немедленно вызывал синхронный `saveSync()`. Два публичных метода предоставляли один и тот же результат с разной формой возврата. Теперь `save(): EditorDocument` синхронен, а `saveSync()` удалён из публичного API.

### Решение

- Оставить синхронный захват структурно разделяемых снимков внутренним механизмом истории.
- Сделать публичный `save(): EditorDocument` синхронным.
- Удалить публичный `saveSync()` из `EditorHandle`, деклараций и документации.
- Внутренний метод назвать по назначению: `captureDocument()` или `saveDocumentSnapshot()`.
- Не допускать асинхронный `BlockPlugin.save()`: загрузка файла и получение метаданных остаются отдельными транзакциями, а документ сохраняет только уже подтверждённый результат.
- Обновить `ChangeNotifier`, чтобы он принимал синхронный снимок и при этом продолжал изолировать ошибки callback.

### Критерии готовности

- `editor.save()` возвращает изолированный `EditorDocument`, а не `Promise`;
- публичное API не содержит `saveSync()`;
- внутренние снимки истории не пересоздают неизменившиеся блоки;
- `onChange(document)` получает новый изолированный снимок;
- повторный `destroy()` остаётся безопасным;
- TypeScript-тесты и package consumer gate проходят.

## 5. Этап 2. Исправить Toggle

### Проблема

Редактор сохраняет поле `open`, но рендерер его не читает. Раскрытый блок после отображения документа становится закрытым.

### Решение

- Передавать `block.data.open` в свойство `HTMLDetailsElement.open`.
- Нормализовать `open` как boolean в редакторе, типах и рендерере.
- Сохранить нативную семантику `<details>/<summary>`.
- Сделать раскрытие в редакторе доступным с клавиатуры: интерактивным должен быть весь заголовок или настоящая кнопка, а не отдельный кликабельный `span`.

### Тесты

- `open: true` создаёт раскрытый `<details>`;
- `open: false` и отсутствие поля создают закрытый `<details>`;
- save/render/save сохраняет состояние;
- undo/redo переключения создаёт один шаг истории;
- управление работает мышью и клавиатурой.

## 6. Этап 3. Переработать Mention

### Подтверждённые проблемы

- глобальный `document.beforeinput` устанавливается при создании плагина;
- обработчик ищет упоминание во всём документе и не проверяет владельца редактора;
- один `globalCtx` перезаписывается последним `hydrate()` или `onEdit()`;
- при нескольких редакторах событие может попасть в чужой контекст и историю;
- создание плагина имеет побочные эффекты до успешной регистрации;
- `editable: false` противоречит фактическому редактированию содержимого и нигде не используется ядром;
- комментарий о том, что ядро не уничтожает внутристрочные плагины, устарел;
- нет функциональной браузерной матрицы поиска, выбора, редактирования и пагинации.

### Архитектура после рефакторинга

- Не устанавливать глобальные обработчики в `createMentionPlugin()`.
- Добавить явный lifecycle внутристрочного плагина: `mount(context)` и `destroy()` либо передавать корневой элемент редактора при регистрации.
- Слушать `beforeinput` на `editor.rootElement` или проверять `root.contains(span)` перед обработкой.
- Хранить контекст по корневому редактору или по виджету, а не в одной переменной.
- Одна активная сессия может существовать только внутри одного экземпляра плагина и одного редактора.
- `AbortController` должен отменять поиск, подгрузку следующей страницы и обработчики сессии.
- Удалить неиспользуемое поле `editable` из публичного контракта либо определить и реально применять его семантику.
- Конструктор/фабрика плагина не должны оставлять listener или stylesheet при неуспешном `createEditor()`.

### Тесты

- ввод `@`, поиск, выбор мышью и клавиатурой;
- `noResults`, `loading`, ошибка поиска;
- пагинация через `nextPageUrl`;
- повторное редактирование существующего упоминания;
- Backspace/Delete на границах виджета;
- программная вставка;
- undo/redo вставки, редактирования и удаления;
- два редактора на одной странице не воздействуют друг на друга;
- destroy во время запроса не изменяет DOM и не оставляет listener;
- повторное создание после destroy работает корректно.

## 7. Этап 4. Реализовать Poll

Детальный формат уже описан в `PLUGIN_DEVELOPMENT_PLAN.md`. В рамках рефакторинга нужно довести его до кода и типов.

### Разделение состояния

Документ хранит авторскую конфигурацию:

```ts
interface PollBlockData {
  pollId?: string
  question: string
  type: 'single' | 'multiple'
  options: Array<{ id: string; text: string }>
  resultsMode: 'always' | 'afterVote' | 'hidden'
  initialResults?: PollResults
}
```

Актуальные голоса, проголосовавшие и голос текущего пользователя являются runtime-состоянием и не должны засорять undo/redo авторского документа.

### Серверный адаптер

```ts
interface PollDataSource {
  load(context: { pollId: string; signal: AbortSignal }): Promise<PollResults>
  vote(context: {
    pollId: string
    optionIds: string[]
    revision?: string
    signal: AbortSignal
  }): Promise<PollResults>
  subscribe?(context: {
    pollId: string
    signal: AbortSignal
    onUpdate(results: PollResults): void
    onError(error: unknown): void
  }): void | (() => void)
}
```

Если сервер использует непрозрачные строки `revision` и может доставлять обновления не по порядку, host передаёт `compareRevisions(next, current)`. Только host знает порядок таких значений; без функции разные ревизии применяются в порядке получения, а одинаковые игнорируются.

### Обязательная функциональность

- локальное голосование без `dataSource`;
- одиночный и множественный выбор;
- загрузка актуального состояния;
- отправка новых голосов;
- получение новых голосов через `subscribe()`;
- отображение проголосовавших, если backend предоставляет эти данные;
- состояния loading, submitting, empty и error;
- защита от двойной отправки;
- отмена запросов и подписки при смене `pollId`, удалении блока и destroy;
- защита от устаревших ответов через `revision` и явный `compareRevisions`;
- push-обновление не отменяет выполняющийся `vote()` и не разрешает повторную отправку;
- сортировка вариантов, раз она заявлена в документации;
- безопасное отображение имени и avatar без произвольного HTML;
- серверные обновления не создают шаги истории документа.

### Документация

- Исправить JSON-пример: минимум два варианта и стабильные `id`.
- Удалить утверждение о функциональности, пока она не реализована.
- Описать локальный режим.
- Добавить точные REST, SSE и WebSocket-примеры реализации одного `PollDataSource`.
- Объяснить границу между данными документа и runtime-результатами.

### Тесты

- локальный режим;
- `load`, `vote`, `subscribe`;
- проголосовавшие и `votersTotal`;
- одинаковые, устаревшие и пришедшие не по порядку revision;
- обновление подписки во время незавершённого `vote()`;
- destroy/abort;
- одиночный и множественный выбор;
- сортировка вариантов с одним шагом undo/redo;
- серверные обновления отсутствуют в истории;
- renderer и editor используют один формат данных.

## 9. Этап 6. Сделать Code экземплярно-изолированным

### Проблема

Highlight.js хранится в модульной глобальной переменной, а после ленивой загрузки Code повторно подсвечивает все `.oe-code-wrap` в `document`. Один редактор может заменить runtime другого.

### Решение

- Создать `HighlightRuntimeProvider` с владением на уровне экземпляра редактора или плагина.
- Не использовать изменяемую модульную переменную для host-provided `hljs`.
- После загрузки обновлять только блоки, принадлежащие текущему плагину.
- Для общего встроенного runtime разрешить неизменяемый кеш Promise загрузки, но не общую изменяемую конфигурацию.
- Освобождать список подписчиков при destroy.

### Тесты

- два редактора с разными runtime не влияют друг на друга;
- ленивое завершение не обновляет уничтоженный блок;
- выбранный язык и autodetect работают;
- повторный render не дублирует классы и listeners.

## 10. Этап 7. Строгая схема данных плагинов

### Общая проблема

`validationMode: 'strict'` сейчас проверяет в основном наличие верхнеуровневых полей. Некоторые malformed-данные принимаются, после чего render молча нормализует, обрезает или заменяет их.

### Требования к валидаторам

- валидатор не изменяет входные данные;
- strict отклоняет документ, который нельзя восстановить без потери данных;
- preserve сохраняет безопасно нормализуемые данные и сообщает `onValidationError`;
- renderer и editor используют одну нейтральную функцию проверки схемы;
- сообщения не содержат пользовательский контент.

### По плагинам

- **Table:** непустой прямоугольный `string[][]`, boolean `withHeadings`.
- **Columns:** допустимый `layout`, точное количество колонок, строковое `content`.
- **Gallery:** массив изображений с допустимым URL и корректными options/styles.
- **Poll:** допустимый тип, минимум два варианта, уникальные `id`, непустой текст, корректные результаты.
- **Checklist:** массив элементов с корректными `text` и `checked`.
- **Embed:** поддерживаемый service, корректный videoId и безопасные media URL.
- **LinkPreview:** только HTTP(S) и разрешённые относительные ссылки по явно выбранной политике; допустимый template.
- **Image, Attaches, Person:** проверить вложенные URL и числовые поля до render.

### LinkPreview отдельно

Сейчас URL из исходных данных сохраняется как любая непустая строка. DOM-защита блокирует опасный `href`, поэтому подтверждённого XSS нет, но невалидное значение остаётся в JSON. Валидация и нормализация должны использовать общую URL policy до сохранения.

## 11. Этап 8. Заменить `document.write()` в Raw

### Решение

- Использовать sandboxed iframe с `srcdoc` или безопасную DOM-загрузку.
- Sandbox остаётся без `allow-scripts` и `allow-same-origin`.
- Пересоздавать iframe при смене preview, не сохранять ссылки на старый документ.
- Не переносить неочищенный Raw HTML в основной document.
- Рендерер продолжает использовать `sanitizeRawHtml`/`setSanitizedRawHtml`.

### Тесты

- script, inline handler, iframe, object и опасные URL не выполняются;
- preview показывает допустимую разметку;
- многократное открытие/закрытие не оставляет iframe и listeners;
- CSP/Trusted Types сценарий рендерера остаётся рабочим.

- «Краткое био» → «Краткая биография».
- «Сбросить стили» → «Очистить форматирование».

### Склонения

Attaches должен использовать `i18n.plural()`:

- 1 файл / 2 файла / 5 файлов;
- 1 вложение / 2 вложения / 5 вложений.

То же правило применяется в редакторе и рендерере.

### Архитектурное исправление scoped i18n

Плагин не должен пытаться получить глобальный `block.back` через локальный scope `plugin.<type>`. Возможные чистые решения:

1. передавать общие действия из ядра уже с готовыми подписями;
2. добавить в scoped API явный `global(key)`;
3. продублировать только действительно плагин-специфичные подписи в пространстве плагина.

Предпочтителен первый вариант: общие команды и их названия принадлежат ядру.

### Тесты

- статически собирать все вызовы `_t()`, `_p()`, `t()` и проверять существование ключей;
- открывать toolbox/settings всех плагинов с русской локалью;
- проверять пользовательские title, placeholder, prompt и aria-label;
- паритет ключей EN/RU остаётся отдельной проверкой, но больше не считается достаточным.

## 13. Этап 10. Доступность интерактивных плагинов

Ручная проверка NVDA/VoiceOver не входит в план, но семантика DOM и клавиатурные тесты обязательны.

### Исправить

- **Person:** вкладки сделать `button`/`tab` с `role="tablist"`, `aria-selected`, клавишами стрелок и клавиатурной перестановкой.
- **Toggle editor:** интерактивный заголовок должен быть кнопкой либо иметь эквивалентную семантику и клавиатурную обработку.
- **Attaches renderer:** раскрываемый заголовок группы сделать кнопкой с `aria-expanded` и `aria-controls`.
- **Poll:** варианты, состояния загрузки, ошибки и результаты должны иметь доступные названия и live-region только там, где это не создаёт шум.
- Все icon-only кнопки получают локализованный `aria-label`.
- Drag-and-drop не должен быть единственным способом изменения порядка.

## 14. Этап 11. Документация и генераторы README

### Источник правды

- Полная документация публикуется через VitePress.
- README конкретного плагина остаётся краткой документацией npm-точки входа и генерируется из проверяемого источника.
- Главный монолитный README редактора не создаётся.
- Исправления вносятся в генераторы, а не только в сгенерированные файлы.

### Подтверждённые ошибки

- Poll обещает сортировку, которой нет.
- Poll показывает невалидный пример с одним вариантом.
- Toggle обещает восстановление `open`, которое рендерер не выполняет.
- LinkPreview в английском тексте называется Bookmark preview.
- Русские примеры местами содержат переводимый английский пользовательский текст.
- Тест README проверяет структуру, JSON, импорты и кодировку, но не семантическое соответствие реализации.

### Требования к каждой странице плагина

- назначение и граница ответственности;
- установка и точная точка входа;
- регистрация;
- полный формат данных;
- все опции конструктора с типами, значениями по умолчанию и ошибками;
- пользовательские действия и их связь с undo/redo;
- lifecycle и владение внешними ресурсами;
- безопасность URL/HTML;
- стили, классы и CSS custom properties;
- renderer и различия между редактором и отображением документа;
- рабочий минимальный пример;
- ограничения и явно не реализованные возможности.

### Публичные callback редактора

Документация конфигурации должна явно, с рабочими примерами, фиксировать:

- `onReady()` вызывается один раз в микрозадаче после возврата `createEditor()` и не вызывается, если редактор успели уничтожить;
- `onChange(document)` не вызывается для исходной загрузки, объединяет последовательные изменения через настраиваемый debounce и получает изолированный актуальный документ;
- ошибка сохранения не передаёт устаревший документ в `onChange`;
- callback, ожидающий выполнения после `destroy()`, подавляется;
- `onChange` не является транспортом на backend: сохранение, повторные попытки и обработка сетевых ошибок принадлежат приложению.

### Терминология расширений

- **Внутристрочный инструмент** изменяет формат выделенного текста и обычно не создаёт самостоятельных сериализуемых сущностей.
- **Внутристрочный плагин** создаёт сериализуемый виджет внутри текстового поля, имеет собственный тип, данные, hydrate и lifecycle.
- Документация должна отдельно и полностью показывать создание обоих типов расширений.
