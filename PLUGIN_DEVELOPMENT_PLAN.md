# План развития плагинов Rector

Документ фиксирует архитектурные решения и результат выполненного цикла. Локализация проверена автоматическими тестами, Carousel реализован как самостоятельный блок, Poll разделяет данные документа и локальное либо серверное состояние. Оставшиеся пункты используются как проверочный список для дальнейших изменений.

## Цели

1. Исправить пользовательские названия и русские переводы существующих плагинов.
2. Добавить самостоятельный блок Carousel, не смешивая его контракт с Gallery.
3. Переработать Poll так, чтобы он одинаково корректно работал локально и с серверным источником данных.
4. Сохранить атомарные undo/redo, детерминированную сериализацию, безопасность и освобождение ресурсов.
5. Не урезать существующие возможности Gallery и Poll.

## Этап 1. Терминология и локализация

- `LinkPreview` отображать как «Превью ссылки», а не «Закладка».
- Проверить названия, подписи, подсказки, меню добавления и настройки всех 21 блока в `locale/ru.js`.
- Разделить пользовательские подписи и внутренние идентификаторы: типы `linkPreview`, `poll`, `gallery` и будущий `carousel` не переводятся.
- Проверить английский и русский словари на одинаковый набор ключей.
- Добавить тест паритета локалей и тест фактических подписей toolbox.

Критерий готовности: в интерфейсе и документации используются одинаковые понятные названия, а отсутствие перевода обнаруживается тестом.

## Этап 2. Новый блок Carousel

### Граница ответственности

Carousel — последовательность самостоятельных слайдов с навигацией. Gallery остаётся коллекцией изображений с раскладкой и просмотром. Новый блок не должен быть псевдонимом Gallery и не должен зависеть от её DOM.

### Предлагаемый формат данных

```ts
interface CarouselBlockData {
  slides: Array<{
    id: string
    type: 'image' | 'video' | 'html'
    src?: string
    alt?: string
    caption?: string
    poster?: string
    html?: string
  }>
  options: {
    loop: boolean
    autoplay: boolean
    autoplayDelay: number
    navigation: boolean
    pagination: boolean
    thumbnails: boolean
    aspectRatio?: string
  }
}
```

### Архитектура

- `plugins/carousel` отвечает за редактирование слайдов, порядок, подписи и настройки.
- `renderer/renderers/carousel` создаёт экземпляр `@shelamkoff/carousel` и полностью владеет его lifecycle.
- Загрузку файлов предоставляет host через `uploadFile`; ядро не знает о сети.
- Для пользовательских источников используется тот же контракт `actions`, что у Image и Gallery.
- Завершённое добавление, удаление, сортировка или изменение настройки создаёт ровно один шаг истории.
- Асинхронная загрузка выполняется вне команды; в историю атомарно попадает только подтверждённый результат.
- URL проверяются общей media policy; пользовательский HTML очищается до монтирования.
- `destroy()` отменяет загрузки, удаляет object URL, listeners, observers и экземпляр Carousel.

### Публичные точки входа

- `@shelamkoff/rector/plugins/carousel`
- `@shelamkoff/rector/renderer/renderers/carousel`
- async presets должны загружать тип `carousel` только при наличии такого блока в документе.

### Проверки

- схема и валидация каждого типа слайда;
- добавление, удаление, сортировка, настройки и upload в undo/redo;
- отказ загрузки не меняет документ;
- повторный render/destroy не оставляет ресурсов;
- клавиатурное управление и состояния ARIA;
- совместимость светлой и тёмной тем;
- package consumer и README для редактора и рендерера.

## Этап 3. Poll с локальным и серверным состоянием

### Разделение данных

Сериализованный документ хранит конфигурацию опроса, но не считается единственным источником актуальных голосов.

```ts
interface PollBlockData {
  pollId?: string
  question: string
  type: 'single' | 'multiple'
  options: Array<{ id: string; text: string }>
  resultsMode: 'always' | 'afterVote' | 'hidden'
  initialResults?: PollResults
}

interface PollResults {
  revision?: string
  total: number
  options: Array<{ id: string; votes: number }>
  voters?: Array<{
    id: string
    name?: string
    avatar?: string
    optionIds?: string[]
  }>
  votersTotal?: number
  currentUserVote?: string[]
}
```

`question`, `type`, `options` и `resultsMode` принадлежат документу. Актуальные счётчики, проголосовавшие и голос текущего пользователя принадлежат runtime-состоянию и приходят через адаптер.

### Адаптер backend

```ts
interface PollDataSource {
  load(context: { pollId: string; signal: AbortSignal }): Promise<PollResults>
  vote(context: {
    pollId: string
    optionIds: string[]
    revision?: string
    signal: AbortSignal
  }): Promise<PollResults>
  subscribe?(context: {
    pollId: string
    signal: AbortSignal
    onUpdate(results: PollResults): void
    onError(error: unknown): void
  }): void | (() => void)
}
```

Host сможет реализовать REST + polling, SSE, WebSocket или собственный transport без зависимости плагина от конкретного backend.

Непрозрачные ревизии не имеют универсального порядка. Если транспорт может доставлять обновления не по порядку, host передаёт в конфигурацию Poll функцию `compareRevisions(next, current)`. Результат больше нуля означает более новую ревизию. Без этой функции разные ревизии применяются в порядке поступления, а одинаковые игнорируются.

### Поток данных

1. При монтировании блок показывает `initialResults` либо состояние загрузки.
2. `load()` получает актуальный snapshot и его `revision`.
3. Голос отправляется через `vote()`; оптимистическое обновление отключено по умолчанию, чтобы не показывать неподтверждённые данные.
4. Ответ `vote()` полностью заменяет runtime snapshot.
5. `subscribe()` передаёт новые голоса и изменения проголосовавших с backend.
6. Одинаковая `revision` игнорируется. Устаревшую ревизию можно определить только через `compareRevisions`; без неё разные непрозрачные значения применяются в порядке получения.
7. При смене `pollId`, удалении блока или `editor.destroy()` запросы и подписка отменяются.

### Локальный режим

- Без `dataSource` сохраняется текущее автономное поведение.
- Локальные голоса меняют сериализованные данные одним шагом истории.
- При наличии `dataSource` серверные результаты не засоряют историю документа; история охватывает только авторскую конфигурацию опроса.

### Проголосовавшие

- `voters` опционален: backend сам определяет доступность и объём персональных данных.
- Плагин не выводит email, IP и произвольный HTML.
- Имя и avatar отображаются только через безопасные DOM-операции и URL policy.
- Для больших списков нужны `votersTotal` и отдельная пагинируемая загрузка; первая версия ограничивает встроенный snapshot настраиваемым максимумом.

### Ошибки и состояния

- отдельные состояния initial loading, refresh, submitting, empty и error;
- повторная отправка доступна только после завершения предыдущей;
- ошибки host получает через `onError`, интерфейс — через локализованный безопасный текст;
- ошибки `load()`, `vote()`, `subscribe()` и `compareRevisions()` передаются в `onError`; автоматического повтора голоса нет;
- callback после destroy не может менять DOM.

### Проверки

- локальный режим без регрессий;
- load/vote/subscribe и обновления проголосовавших;
- out-of-order ответы, conflict revision, abort и destroy;
- отсутствие двойного голоса при повторном клике;
- сохранение выбора single/multiple;
- безопасность URL и персональных полей;
- доступность loading/error/results;
- отсутствие серверных обновлений в undo/redo;
- README с REST, SSE и WebSocket-примерами адаптера.

## Принятые решения

- формат `CarouselBlockData` зафиксирован в публичных декларациях;
- `voters` содержит только безопасно отображаемые данные, `votersTotal` передаёт полный размер списка;
- встроенный список ограничивается `maxVoters`; пагинация принадлежит host и не входит в контракт первой версии;
- повторное голосование разрешено контрактом: `currentUserVote` позволяет серверу заменить предыдущий выбор;
- порядок непрозрачных ревизий задаётся только явной функцией `compareRevisions`.
