# Архитектура

Rector разделяет хранимый документ, среду редактирования, расширения и рендерер документа. Эти уровни используют общие контракты данных, но не общие изменяемые диспетчеры или состояние интерфейса.

## Границы системы

```text
Приложение
  │
  ├─ createEditor(config) ──> Дескриптор редактора
  │                           ├─ API блоков
  │                           ├─ подписки на события
  │                           └─ save/render/destroy
  │
  ├─ Блочные и внутристрочные расширения
  │      └─ scoped context / DataTask authority
  │
  └─ createEditorRenderer(config) ──> DOM документа

Версионированный документ JSON — контракт между редактированием, хранением и отображением.
```

## Граница приложения

Приложение создаёт и уничтожает редактор, передаёт конфигурацию, сохраняет документы и подписывается на публичные события. Оно получает узкий дескриптор `IEditor`, а не внутренние объекты сборки.

Дескриптор намеренно не предоставляет диспетчер блоков, диспетчер команд, диспетчер истории, диспетчер выделения, генератор событий, диспетчер всплывающих элементов или загрузчик стилей. Поэтому прикладной код не может обойти целостность документа.

## Граница документа

`EditorDocument` содержит обычные сериализуемые данные одного явного текущего формата. Rector строго проверяет оболочку на входе и возвращает независимую копию при `save()`. Отсутствующие, старые и будущие версии документа или схемы отклоняются. Миграции и режим сохранения старого формата не входят в среду выполнения. Живой DOM не является хранилищем документа.

У каждого блока есть устойчивый `id`, зарегистрированный `type`, принадлежащие плагину `data` и необязательные поля `revision`, `tunes` и `inline`. Ядро владеет оболочкой и идентификаторами, а плагин — только формой собственных `data`. Принадлежащая источнику `revision` служит оптимизацией частичного отображения, а не ещё одной версией схемы.

Версия документа описывает сериализованную оболочку и общие правила плагинов. У каждой схемы блока или внутристрочного виджета есть точный `currentVersion`; сериализованный `dataVersion` должен совпадать с ним. При необходимости приложение преобразует исторические данные вне Rector до передачи текущего документа.

## Граница сборки редактора

`createEditor()` собирает редактор: проверяет конфигурацию текущего формата, создаёт владельца канонического документа, подготавливаемые транзакции, проекцию и восстановление, выделение, историю, обработчики клавиатуры и нативного ввода, панели, импорт из буфера обмена, диагностику, локализацию и владельцев стилей.

Эти службы взаимодействуют через узкие внутренние интерфейсы. Они остаются деталями реализации, даже если в исходном дереве есть файл деклараций. Публичные импорты ограничены путями из карты `exports` пакета.

## Граница команды

Каждое постоянное действие проходит через одну транзакцию. Ядро создаёт черновик, подготавливает проекцию и историю, применяет новую проекцию и одновременно фиксирует модель с историей. Затем оно освобождает прежние ресурсы и публикует неизменяемые события. Ошибка до фиксации восстанавливает предыдущую проекцию без изменения модели и истории; невозможность восстановления прекращает дальнейшие изменения.

Команды приложения и полномочия пользователя или плагина разделены, особенно в режиме чтения. Экземпляр блока или виджета получает ограниченные `updateData()`, защищённую операцию изменения DOM и отзывную `beginTask()` вместо внутренних диспетчеров. Подробности: [Команды и история](/ru/guide/commands-history).

## Границы расширений

В Rector есть четыре разные роли расширений:

| Роль | Чем владеет | Чем не владеет |
| --- | --- | --- |
| Блочный плагин | редактируемым DOM одного блока и его сериализованными `data` | порядком документа, идентификатором блока и общей историей |
| Внутристрочный инструмент | форматированием выделенного диапазона | постоянными данными виджета |
| Внутристрочный плагин | виджетом в тексте и его сериализованными данными | схемой окружающего блока |
| Рендерер блока | итоговым DOM одного типа блока | элементами управления и состоянием редактора |

Расширения получают возможности, а не внутренние диспетчеры. Плагин может изменить собственный элемент через переданный контекст, но не может переставлять произвольные блоки или создавать внутренние события.

## Владение стилями

Приложение импортирует основную таблицу стилей Rector. Определение плагина может объявить URL таблиц стилей. Rector подсчитывает владельцев соответствующих элементов `<link>` между экземплярами редактора. После уничтожения последнего владельца подключённая таблица удаляется.

У рендерера документа отдельный жизненный цикл стилей. `renderer.injectStyles()` возвращает владельца, чей метод `destroy()` освобождает эти подключения. Симметричное освобождение предотвращает утечки глобальных стилей.

## Владение ресурсами

У каждой подписки и каждого выделенного ресурса должен быть владелец:

- редактор владеет обработчиками корневого элемента, наблюдателями, внутренними диспетчерами, всплывающими элементами и зарегистрированными экземплярами плагинов;
- смонтированный экземпляр блока владеет своими обработчиками и сторонними объектами, освобождая их в `destroy()`; полномочия изменения отзываются до освобождения ресурсов;
- группа внутристрочных элементов управления освобождает временные элементы в своём `destroy()`;
- рендерер владеет экземплярами рендереров, подключёнными к контейнерам результата, и освобождает их через `destroy(container?)`;
- приложение владеет дескриптором редактора и каждым созданным владельцем стилей рендерера.

Расширение не должно откладывать освобождение ресурсов до выгрузки страницы.

## Поток данных

### Исходная загрузка

1. Приложение передаёт текущий документ `2.0.0` в `createEditor()`.
2. Единая граница текущего формата проверяет оболочку, идентификаторы блоков и точные версии зарегистрированных схем до изменения живого состояния.
3. Реестр создаёт независимые снимки повторно используемых определений и отдельную среду каждого плагина для редактора.
4. Проекции блоков и виджетов подготавливаются с временными контекстами и получают полномочия только после успешного подключения и фиксации.
5. Канонические ссылки виджетов отображаются только из карты `inline` блока; внешний HTML, похожий на виджет, не декодирует данные.

### Редактирование и сохранение

1. Команда приложения, нативный ввод, действие панели или контекст расширения входит в общую границу команды.
2. Операции с данными собирают полные канонические записи. Защищённое изменение форматированного текста затрагивает только зарегистрированные поля проекции и синхронно сериализует изменённые блоки.
3. Транзакция подготавливает проекцию и историю до фиксации модели.
4. Виджеты сериализуются обратно в ссылки и карту `inline` блока; общие канонические преобразования разрешают коллизии и сохраняют буквальный текст.
5. `save()` экспортирует независимые текущие данные; асинхронная работа сохраняет результат только через действующую `DataTask`.

### Отображение документа

1. Приложение передаёт сохранённый JSON в `EditorRenderer`.
2. Рендерер выбирает `BlockRenderer` по значению `type` блока.
3. Зарегистрированные внутристрочные записи проходят точную текущую схему, а их ссылки отображаются отдельными рендерерами виджетов.
4. Рендерер блока возвращает итоговый DOM.
5. `destroy()` освобождает ресурсы рендерера при замене или удалении контейнера.

## Направление зависимостей

Ядро не импортирует код приложения. Блочные плагины зависят от публичных контрактов и небольших общих утилит. Рендерер зависит от контракта документа, но не от среды редактирования. Необязательные интеграции загружаются только возможностями, которым они нужны.

Сохраняйте это направление в собственных расширениях: опирайтесь на экспортируемые типы и возможности контекста, но не импортируйте файлы из `core/`, которых нет в `exports` файла `package.json`.
