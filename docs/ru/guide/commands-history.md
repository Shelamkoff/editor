# Команды и история

Одно завершённое действие создаёт один шаг истории: форматирование нескольких блоков, настройки, вставка, разделение, объединение и действия плагинов.

## Что такое команда

Команда синхронно подготавливает канонические данные, проекцию и историю до единой точки фиксации. При ошибке прежняя модель и проекция восстанавливаются без нового шага истории. Если восстановление проекции невозможно, редактор прекращает изменения; зафиксированные данные остаются доступны через `save()`.

Повторный синхронный вход во время подготовки, применения или уведомления о фиксации запрещён. Приложение использует `editor` и `editor.blocks`; экземпляры расширений получают ограниченные возможности контекста.

## Команды из прикладного кода

Команды адресуют блоки по стабильным идентификаторам. Каждый вызов ниже создаёт один шаг истории:

```js
const insertedId = editor.blocks.insert(
  { type: 'paragraph', data: { text: 'Новый абзац' } },
  editor.blocks.count,
)
editor.blocks.convert(insertedId, { type: 'heading', toolboxItemId: 'h2' })
```

`render(document)` принимает только текущий формат и атомарно заменяет документ. `clear()` создаёт пустой блок по умолчанию. Команды приложения доступны в режиме чтения; пользовательские изменения, отмена и повтор заблокированы.

## Команды из блочного плагина

`create(initial, context)` получает `BlockInstanceContext`. Вызывайте `context.updateData(producer)` один раз для завершённого действия с данными. Синхронный обработчик получает текущие данные; его результат проходит схему и отображается после фиксации.

```js
function createCounterInstance(initial, context) {
  const root = context.ownerDocument.createElement('div')
  const button = context.ownerDocument.createElement('button')
  const value = context.ownerDocument.createElement('span')
  button.textContent = '+1'
  const project = data => { value.textContent = String(data.count) }
  project(initial)
  button.addEventListener('click', () => {
    context.updateData(current => ({ ...current, count: current.count + 1 }))
  }, { signal: context.signal })
  root.append(value, button)
  return {
    element: root,
    update: project,
    setReadOnly: readOnly => { button.disabled = readOnly },
    destroy() {},
  }
}
```

`context.commitDomMutation(operation)` предназначен для синхронных защищённых изменений зарегистрированных полей форматированного текста. Ядро сериализует и проверяет затронутые поля внутри транзакции. Фокус, наведение и открытие меню не создают историю.

Не вызывайте команды изменения данных и не переключайте режим read-only внутри этого DOM-обработчика. Rector отклоняет вложенную запись до вызова её обработчика данных и восстанавливает зафиксированную проекцию. Если чтение или валидация завершились ошибкой и восстановить проекцию не удалось, дальнейшие изменения прекращаются; `save()` по-прежнему возвращает зафиксированную модель. Выброшенный `AggregateError` сохраняет исходную ошибку и ошибку восстановления.

Подготовка проекции, публикация и переход read-only также отклоняют вложенные команды до обработчика данных. В этих защищённых операциях нельзя начинать задачу изменения данных (`DataTask`). Неудачная смена режима восстанавливает все затронутые controls, включая обработчик, который изменил их перед исключением. Защищённое редактирование запоминает направленное выделение до DOM-обработчика и его конечную каретку до повторной проекции; восстановление после ошибки, отмена и повтор возвращают соответствующие позиции.

`context.requestSplit()` и `context.requestExit()` запрашивают структурные действия; не имитируйте их событиями клавиатуры. Возможности составного редактирования возвращают данные вместе со структурным намерением для одной транзакции.

## Команды через `/`

Ввод `/` открывает меню команд. В пустом блоке оно предлагает зарегистрированные блочные плагины. Если зарегистрированы внутристрочные плагины, меню также может открываться после уже введённого текста и предлагать подходящие внутристрочные виджеты. Пункты автоматически формируются из массивов `plugins` и `inlinePlugins`; отдельного списка команд в конфигурации нет.

Текст после `/` фильтрует пункты по типу плагина и его локализованному названию. Меню располагается непосредственно под текстом `/запрос`, а не у левого края блока. При прокрутке контейнера оно следует за командой, а при недостатке места снизу открывается над ней.

| Клавиша или действие | Результат |
| --- | --- |
| `ArrowDown` / `ArrowUp` | Перемещение по отфильтрованным пунктам. |
| `Enter` или `Tab` | Выполнение активной команды. |
| Нажатие указателем | Выполнение выбранной команды без потери выделения редактора. |
| `Escape` | Удаление текущего текста `/запрос` и закрытие меню. |
| `Backspace`, когда остался только `/` | Закрытие меню; символ `/` удаляет браузер. |

Если текущий блок содержит только `/запрос`, выбор блочного пункта преобразует его на месте. Если перед командой уже есть содержимое, Rector удаляет только `/запрос`, сохраняет исходный блок и вставляет выбранный блок сразу после него. Выбор внутристрочного пункта удаляет `/запрос` и вставляет виджет точно в эту позицию. Каждый вариант записывается как одна команда, поэтому одна отмена возвращает состояние до выбора. Стили меню задаются классом `.oe-slash-menu` и его дочерними классами, перечисленными в разделе [«Стили и темы»](/ru/guide/styling).

## Преобразование выделения внутри блока

Переключатель типа позволяет преобразовать выделение, не заменяя весь исходный блок. Обычный текстовый блок разделяется на содержимое до выделения, новый блок и содержимое после выделения. Вся операция создаёт один шаг истории.

Полное и частичное преобразование сохраняет связанные внутристрочные виджеты, если целевой тип способен их представить. Rector сохраняет данные и идентичность ссылок. Преобразование, которое превратило бы виджет в обычный текст или потеряло его данные, отклоняется до изменения документа и истории. Строка вида `{{id}}` без соответствующей записи карты виджетов остаётся обычным текстом.

Плагин List обрабатывает данные списка и не передаёт разметку `<li>` универсальному разделителю HTML:

1. выделенное содержимое удаляется из исходного списка;
2. новый блок вставляется сразу после оставшегося списка;
3. оставшиеся пункты нумерованного списка находятся в одном `<ol>`, поэтому браузер перенумеровывает их;
4. при выборе текстового типа выделенная внутристрочная разметка становится полем `text` нового блока;
5. при выборе нетекстового типа выделение удаляется, а новый блок получает исходные данные выбранного плагина;
6. если выделены все пункты, исходный список удаляется, а новый блок занимает его позицию.

Отмена и повтор атомарно восстанавливают и список, и вставленный блок. Автор расширения может реализовать такое же поведение методом `capabilities.conversion.partial`, описанным в разделе [«Создание расширений»](/ru/guide/extensions#преобразование-части-данных).

## Команды из внутристрочных инструментов

Встроенная панель направляет форматирование через изменение диапазона. Пользовательский инструмент получает один из двух контекстов:

- `InlineMutationContext` в `onMount(button, mutations)` для непосредственного действия;
- `InlineToolActionContext` в `renderActions(ctx)` для панели, работающей с сохранённым выделением.

```js
renderActions(ctx) {
  const apply = document.createElement('button')
  apply.textContent = 'Применить'

  apply.addEventListener('click', () => {
    ctx.restoreSelection()
    ctx.mutate(() => applyStyleToRange(ctx.range))
    ctx.close()
  })

  return apply
}
```

Полужирное и курсивное начертание, создание и удаление ссылки, цвет, выравнивание, размер шрифта и очистка форматирования используют эту же границу. Одно нажатие инструмента нельзя делить на несколько вызовов `mutate()`.

Полный контракт инструмента, правила регистрации, названия встроенных типов, панели действий и отличие от постоянных виджетов описаны в разделе [Внутристрочные инструменты и плагины](/ru/guide/inline-extensions).

## Команды из элементов управления блока

Специальные элементы блока во внутристрочной панели используют model-first возможность `inlineControls`. Каждое действие получает канонические данные блока и возвращает обновлённые данные через тот же контракт `SettingsActionCapability`, что и обычные настройки блока.

Элемент управления не владеет редактируемым DOM и не уведомляет Rector после изменения проекции. Rector фиксирует возвращённые данные одной транзакцией и согласует проекцию; выделение и история остаются внутри среды документа.

## Команды из внутристрочных виджетов

Каждый смонтированный внутристрочный виджет получает `InlineWidgetContext`. Состояние принадлежит модели: читайте его через `getData()`, а одно завершённое действие фиксируйте одним вызовом `updateData()`.

```js
create(id, initial, context) {
  const button = document.createElement('button')
  button.textContent = initial.enabled ? 'Вкл.' : 'Выкл.'

  button.addEventListener('click', () => {
    context.updateData(current => ({
      ...current,
      enabled: !current.enabled,
    }))
  }, { signal: context.signal })

  return {
    element: button,
    update(next) {
      button.textContent = next.enabled ? 'Вкл.' : 'Выкл.'
    },
    setReadOnly(readOnly) {
      button.disabled = readOnly
    },
    destroy() {},
  }
}
```

DOM виджета — только проекция канонических данных. Не изменяйте DOM с последующим уведомлением Rector; фиксируйте изменение через `updateData()`, чтобы состояния до и после изменения, отмена/повтор и защита от устаревших обработчиков оставались атомарными.

## Асинхронная работа

Сохраняйте асинхронные результаты через отзывную задачу `DataTask`; обработчики данных и изменения DOM остаются синхронными.

```js
button.addEventListener('click', async () => {
  const task = context.beginTask()
  button.disabled = true
  try {
    const uploaded = await uploadFile(file, { signal: task.signal })
    task.commit(current => ({ ...current, url: uploaded.url }))
  } finally {
    task.cancel()
    if (!context.signal.aborted) button.disabled = context.isReadOnly()
  }
}, { signal: context.signal })
```

Замена документа, уничтожение, смена поколения и переход в режим чтения отзывают задачу. Устаревшая задача возвращает `false`, не вызывая обработчик данных; возврат к редактированию её не возобновляет.

## Буфер обмена и составные выделения

Rector использует один приватный MIME — `application/x-rector-fragment` с `version: 2`. Фрагмент строится из канонической модели. Части форматированного текста сохраняют оформление и только реально используемые записи виджетов; части целых или структурных блоков исключают идентификаторы блоков и ревизии источника. Приватное представление имеет приоритет над `text/html` и `text/plain`; ошибочная, старая или будущая версия отклоняет вставку без перехода к стандартным представлениям.

Для составных блоков `BlockCapabilities.clipboard.slice(data, context)` одновременно определяет экспортируемые `parts` и остаток `remaining`. Копирование и вырезание используют одну границу данных: обнаруженная ошибка подготовки или записи обязательного приватного MIME не удаляет исходное содержимое. Список, чек-лист, колонки, таблица, цитата, предупреждение, переключатель и спойлер сохраняют структуру; общий путь форматированного текста применяется к одному простому выбранному полю.

Вставка поверх составного выделения сначала проверяет фрагмент и сохранённый план цели с поколением и ревизией, затем выполняет одну транзакцию. Одна отмена восстанавливает исходный документ. Внешние HTML, текст и файлы рассматриваются только при отсутствии приватного MIME; асинхронные обработчики завершаются до первого изменения документа.

## Управление отменой и повтором

Внутри корневого элемента редактора зарегистрированы сочетания клавиш с учётом платформы:

| Действие | Сочетание клавиш |
| --- | --- |
| Отменить | `Mod+Z` |
| Повторить | `Mod+Shift+Z` или `Mod+Y` |

`Mod` означает Command в macOS и Control в Windows или Linux. Элементы управления приложения работают с той же историей через публичные методы `editor.undo()` и `editor.redo()`. Оба возвращают `false`, если подходящего шага нет или редактор находится в режиме чтения. Для состояния недоступности кнопок используйте `editor.canUndo`, `editor.canRedo` и событие `history:changed`; обращаться к внутреннему диспетчеру истории не следует.

В обычных элементах `input` и `textarea`, принадлежащих плагину, остаётся собственная отмена браузера. История Rector имеет приоритет только тогда, когда фокус находится в редактируемом содержимом документа или интерфейсе редактора.

## Порядок и объединение истории

История работает по принципу «последним добавлен — первым отменён». Если сначала вставить блок, а потом применить форматирование, первая отмена удалит форматирование, а вторая — вставленный блок. Повтор восстановит действия в обратном порядке.

Непрерывный обычный ввод текста объединяется каноническим механизмом истории. Явные команды, изменение выделения, структурные операции, вставка и действия панелей всегда образуют границу команды.

`canUndo` и `history:changed` реагируют сразу после первого события ввода, открывающего такую группу, поэтому кнопки приложения не ждут окончания задержки. Начало новой ветви ввода также сразу меняет `canRedo` на `false`.

Новое действие после отмены удаляет прежнюю ветвь повтора. Параметр `historyMaxStack` задаёт ёмкость истории, а `historyCoalesceMs` — интервал объединения нативного ввода.

## События наблюдают, но не выполняют команды

`editor.on()` позволяет только подписываться. События сообщают о завершённом поведении; прикладной код и плагины не должны создавать их самостоятельно.

```js
const stopHistoryState = editor.on('history:changed', ({ canUndo, canRedo }) => {
  undoButton.disabled = !canUndo
  redoButton.disabled = !canRedo
})

const stopDirtyState = editor.on('transaction:committed', () => {
  markDocumentDirty()
})

// Позже
stopHistoryState()
stopDirtyState()
```

`history:changed` сообщает о доступности команд, `transaction:committed` — о записанном шаге, а `document:changed` — об изменении документа. `onChange` — отложенное сериализованное уведомление, предназначенное для сохранения. Переход между режимами отправляет `history:changed`, но не отправляет `transaction:committed`, `document:changed` и не вызывает `onChange`.

## Проверка расширения

Перед публикацией интерактивного расширения проверьте все последовательности:

1. выполните действие, отмените один раз и сравните полный документ с исходным;
2. повторите один раз и сравните документ с результатом действия;
3. после отмены выполните новое действие и убедитесь, что старая ветвь повтора исчезла;
4. заставьте действие выбросить исключение и убедитесь, что ни DOM, ни история не изменились;
5. уничтожьте редактор во время асинхронной работы и убедитесь, что результат проигнорирован;
6. проверьте выделение и фокус после отмены и повтора.
