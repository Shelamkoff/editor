## 3. Подтверждённый дефект и исправление

**R-2026-11-06-01 — отказ регистрации корректных inline paste patterns из другого JavaScript realm.**

- **Файл:** `core/ExtensionRegistry.js`, `snapshotInlineDefinition()`.
- **Исходная причина:** `pattern instanceof RegExp` возвращает `false` для корректного регулярного выражения из другого `Window`/iframe/realm. Это противоречит уже поддерживаемой модели owner-document/foreign-realm и может ломать регистрацию стороннего inline-плагина.
- **Сценарий:** создающий плагин код передаёт native `RegExp` из другого realm в `paste.patterns`; `new ExtensionRegistry(...)` выбрасывает `TypeError`.
- **Решение:** сохраняется быстрый локальный `instanceof`; для foreign-realm используется вызов нативного getter `RegExp.prototype.source` с `Reflect.apply`, проверяющий встроенный `RegExp` brand. Проверка по `Object.prototype.toString` или `Symbol.toStringTag` **не** используется, поскольку её легко подделать. После допуска выполняется существующее копирование `new RegExp(pattern.source, pattern.flags)`; изменяемый объект плагина в реестре не удерживается.
- **Тесты:** позитивный `node:vm` foreign-realm паттерн и негативный поддельный `Symbol.toStringTag`; старый тест отделённого копирования сохранён. Затронуто только определение плагина, никаких изменений в модели документа, истории, HTML-сериализации или поведении иных плагинов.
- **Статус:** код отправлен в `e5f0ec9`, фикстура восстановлена и исправлена в `d1f350e`. Первая CI-итерация `e5f0ec9` выявила синтаксическую ошибку **в добавленном тесте** — эффект специальной последовательности `$'` при программной вставке текста. Это не дефект product runtime. Исходный файл тестов полностью восстановлен из родительского SHA и тесты добавлены без использования подстановки replacement-токенов. Статус окончательной матрицы нужно читать по SHA окончательного коммита; успешный CI исходного SHA не подменяет проверку патча.

**Классификация:** подтверждённая совместимость/расширяемость, низкая сложность исправления, значимая для iframe-потребителей, не свидетельствует о критической уязвимости.

## 5. Безопасность и устойчивость

- **Документ и входные данные:** `DocumentSchema` проверяет формат и версии, плотность массивов, допустимость JSON; `cloneJsonValue` захватывает входные данные и изолирует их от внешней мутации, отклоняет циклы и не-JSON значения.
- **HTML:** узкий allowlist inline-тегов/атрибутов и CSS; Raw использует DOMPurify с дополнительной обработкой URL/CSS; Trusted Types поддерживаются через owner-document policy. При текущем исходном анализе не выявлен подтверждённый обход санитайзера. Это не формальная гарантия отсутствия любых XSS.
- **URL:** отдельные политики `link`, `external`, `media`, `download`, блокировка опасных схем и credentials в network URL. Права загрузки/доступа к внешним файлам остаются обязанностью хост-приложения.
- **Модель расширений:** исполняемый код сторонних плагинов считается доверенным **кодом хоста**, а не sandbox. HTML sanitization не защищает от злонамеренного произвольного JS внутри уже установленного расширения.
- **Async/lifecycle:** `InstanceScope`, `AbortSignal`, управление DOM-ресурсами и отзыв авторитетов протестированы, в проверенных сценариях памяти не обнаружено удержания retired owners. Это не доказательство отсутствия всех возможных утечек.
- **Поставки:** `npm ci` для базового CI сообщал о нуле известных уязвимостей в установленном дереве; по pinned Git dependency npm сообщает, что пропускает integrity check. Привязка к immutable SHA есть; для повышенного supply-chain assurance рекомендована отдельная проверка содержимого артефактов/происхождения, но предупреждение npm само по себе не баг библиотеки.

**Новых подтверждённых уязвимостей безопасности класса release-blocker в рассмотренных границах не выявлено.** Применение в произвольных хост-приложениях требует собственного CSP, проверки загружаемых файлов и доверия к подключаемым плагинам.

### План архитектурной оптимизации (условный — не начинать без измерений)

**P1. Startup/import boundary analysis — средняя сложность, исследование необходимо только при целевой проблеме начальной загрузки.**

1. Снять измерения real consumer bundle: cold import, время создания редактора, parse/execute, long tasks, обработка первого ввода и p95 на средних/крупных документах; включить собственные зависимости, Chromium на слабом CPU.
2. На реальном import graph выделить обязательный минимальный путь и необязательные сценарии (например, лениво активируемые панели/возможности). Не менять контракты до подтверждения стоимости на критическом пути.
3. Если профилирование подтверждает существенный блокирующий код, извлечь **один** устойчивый lazy boundary при сохранении стабильного публичного API, отзывов задач, CSP/Trusted Types, фокуса, истории и SSR-ограничений. Повторить существующий browser, native, heap, package и comparative CI целиком.
4. Принять изменение только при воспроизводимом выигрыше на холодном старте **без** регрессии ввода, истории и памяти.

**Эффект:** потенциально меньше startup CPU/байт в типичной конфигурации. **Риски:** гонки асинхронной загрузки, потеря фокуса/selection, дополнительные запросы сети, рост сложности lifecycle. **Сложность реализации:** высокая, если требуется новый lazy контракт. **Необходимость сейчас:** не доказана, поэтому рефакторинг пока не рекомендован.

**P2. Browser compatibility matrix — средняя сложность, условная необходимость.** Если релиз обещает Firefox/Safari, добавить отдельные нативные IME/clipboard/focus/drag сценарии там, не объявляя Chromium-прогоны доказательством кроссбраузерности. Новую архитектурную абстракцию без воспроизводимой несовместимости не вводить.

**P3. Это профилактика новых локальных дефектов, не повод создавать второй механизм регистрации.

## 7. Релизная оценка и условия

1. Baseline `f46cf769` проходит весь задекларированный CI. Исторические 209/209 obligations закрыты в ограниченном документированном Chromium scope.
2. После **любого** нового commit — включая документацию — итоговый статус следует проверять для **актуального HEAD**. Красный неполный или выполняющийся gate нельзя считать успешным на основании предыдущего SHA. Перед публикацией необходимы green `Verify library` и `Rector v2 comparative audit` именно для release SHA.
3. Публикация пакета в npm, реальный Safari/Firefox, сторонние файловые хосты и системный Drag&Drop остаются вне подтверждённого здесь объёма испытаний. Релиз с заявленной поддержкой Chromium можно оценивать отдельно от более широких обещаний.
4. **Не блокировать релиз** историческими ошибками reference v1, advisory превышением размера на 2 B, отчётным предупреждением Vitepress или простым количеством строк в модуле.
5. **Не сокращать** существующие тесты, native matrix или CI ради лимитов времени/размера. Фактические прогоны и их источники должны оставаться проверяемыми.

**Вывод:** подтверждено одно локальное исправление cross-realm совместимости. В рассмотренных архитектурных границах нет доказанного основания для большой перестройки; наибольший потенциальный выигрыш требует сперва профилирования реальной загрузки. Окончательная отметка «готов к релизу» для нового HEAD зависит от всех его штатных CI-проверок, а не от успешной базовой ревизии.
