## 2. A-06: потеря клавиатурного фокуса после нативного изменения Image Settings

### Воспроизведение и причина

Пользователь открывает Settings изображения, вводит `160px` в Width и нажимает Tab. Библиотека правильно сохраняет ширину одной транзакцией `block.update`, однако фокус остаётся на `BODY`, поэтому клавиатурная история редактора больше не принадлежит ожидаемому элементу.

Регрессия возникла при предыдущем исправлении передачи фокуса в `aa13769d`: безусловное восстановление wrapper было заменено проверкой текущего владельца. Эта проверка покрывала `change` на ещё сфокусированном input, но пропустила нативный переход между старой и следующей целью фокуса.

В рассматриваемом native blur/change-пути браузер уже очистил `activeElement`, когда вызывается обработчик `change`. Следующая цель ещё не получила фокус. Обновление Image заменяет всю форму, удаляя старый input и намеченный следующий control. `retainControlFocus` видел `BODY` на входе, не признавал владельца и пропускал восстановление.

Этот порядок согласуется с исходниками Blink: [`Document::SetFocusedElement`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/core/dom/document.cc) очищает прежний указатель фокуса до вызова `SetFocused(false)`, а [`TextControlElement::SetFocused`](https://chromium.googlesource.com/chromium/src.git/+/c6a621923739984406968919bd48863db84809c8/third_party/blink/renderer/core/html/forms/text_control_element.cc) вызывает отправку `change` для изменённого текстового control при потере фокуса. [Правило HTML о завершении выполнения скрипта](https://html.spec.whatwg.org/multipage/webappapis.html#clean-up-after-running-script) допускает microtask checkpoint при опустевшем стеке JavaScript; поэтому microtask не служит гарантией завершения охватывающего нативного перехода. Эти ссылки объясняют механизм, но не заявляются как точные исходники бинарных сборок CI: первая ведёт на текущую ветку Blink, вторая — на зафиксированную историческую ревизию. Поведение конкретных браузеров подтверждено отдельными RED/GREEN артефактами ниже.

Прежний положительный публичный тест менял значение и отправлял DOM `change`, пока input оставался активным. Он проверял другой, допустимый путь; его успех не доказывал корректность нативного Tab. Поэтому новый контроль использует настоящий браузерный ввод и сохранён наряду со старым.

### Исправление

Изменены только внутренний helper, его тесты и Image:

1. Внутренний обработчик `change` передаёт точный исходный control из своей closure. Контекст публичного API `SettingsPanelContext` не расширяется.
2. Исходный control подтверждает владение только при `activeElement === BODY`, если он ещё подключён, находится внутри нужного wrapper, принадлежит тому же документу и является native form control. Rich-text, чужие и отсоединённые элементы исключаются.
3. Восстановление в этом особом случае переносится в следующую задачу соответствующего окна. Это даёт браузеру завершить исходный переход фокуса; раннее восстановление внутри обработчика или microtask могло бы помешать обычному уходу пользователя во внешнее поле.
4. До завершения задачи сохраняется временное наблюдение `focusin`. Получение фокуса новым элементом отменяет восстановление даже тогда, когда этот элемент затем сам теряет фокус.
5. Перед восстановлением повторно проверяются `BODY` и подключённость wrapper. Слушатель освобождается через `finally`; ошибка операции и удаление wrapper не вызывают позднего возврата фокуса.

Пути, которые входят с уже сфокусированным собственным control, сохраняют синхронное завершение. Канонический commit, его результат и история не откладываются. Изменение не вводит глобальный менеджер фокуса или новое хранилище состояния.

## 3. Постоянная нативная защита от повторения

В `tests/browser/regressions/image-settings-native-focus.js` добавлены четыре сценария:

- ввод Width через `Input.insertText`, Tab и обычное продолжение клавиатурной истории;
- тот же ввод с синхронной передачей фокуса во внешний input из `transaction:committed`;
- тот же ввод с синхронной передачей в соседнее поле редактора, с проверкой текущего блока и точной каретки;
- обычный нативный клик во внешнее поле после ввода Width, без передачи фокуса из обработчика commit.

Проверяются trusted input/change и нативный жест, ровно один `block.update`, сохранение соседнего поля, точные данные и стиль изображения, один нативный Undo/Redo. В обычном Tab-сценарии тест не устанавливает фокус повторно перед Undo: это скрывало бы исходный дефект. В сценариях передачи фокуса отдельное последующее возвращение в редактор выполняется только после проверки нового владельца и отключения observer.

Проверен RED старого реестра и GREEN обновлённого классификатора. Фактическая регистрация полной страницы содержит 120 уникальных сценариев и точные 53 выбранных; эта проверка регистрации сама не исполняет нативные тела.
